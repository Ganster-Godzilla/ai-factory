# T-2026-0902-006 提案:loop 合 main 走受保护路径(交接)

## 问题

编排 loop 各切片在 worktree 干活没问题,但"合 main"这步在共享工作区直接 merge,
无任何保护:2026-09-01 晚实证——交互会话(sk-video-studio 侧)在 main 已
add+commit 的 SOP 文档,被 loop 同窗口的 merge/分支操作挤掉,**该提交未入任何
历史**(reflog 无条目、fsck 无悬挂对象;推送回执实际推的是 loop 的 merge tip
98e3853);文件未丢,次日取证重提。sk 侧已于 2026-09-02 立分支纪律
(T-2026-0902-005,CLAUDE.md 刚性节);但 loop 作为"合 main 的机器"本身无保护,
同类事故还会再发生在任何并发会话身上。

## 方向

loop 合 main 前加"他人未推送/未合入检测"或改受保护合并,三选一做其一
(由 ai-factory 评审裁决,sk 侧不越界):
1. **合前检测**:merge 前查 `git log origin/main..HEAD` 若含非 loop 签名的提交
   (或工作区有非本切片的未提交变更)→ 挂起工单 + 报警,不硬合;
2. **FF-only 合并**:`git merge --ff-only` 失败即挂起人工裁决(防覆盖式合并);
3. **合并审计**:loop 的每次合 main 操作写事件流(actor=loop、基线 hash、
   合并前后 HEAD),出事可追溯(配合 sk 侧 reflog 取证先例)。

## 范围

- ai-factory 侧评审与实现(orchestrator/daemon 的合并/补入账逻辑);
- sk 侧仅提供实证材料(本提案 + sk-video-studio reflog 取证过程)。

## 不做

- sk 侧不动管道代码;不重构 loop 的 worktree 机制(那部分是好的);
- 不引入 GitHub 分支保护(本地规矩先行,平台保护后议);
- 不追溯昨夜事故责任(已修复,重在防再犯)。
