# 提案:L1 驾驶员模型切 k3.1-pro

## 问题

编排器 L1 工单的执行层驾驶员当前靠 claude CLI 全局默认模型(`k3`)隐式决定——
runner 不传 `--model`(claude_code.py `DRIVER_MODELS` 白名单仅 k2.6/gpt-6-astra)。
kimi coding 订阅池现已提供 **k3.1-pro / k3.1-pro-highspeed**(2026-10-28 经生产 relay
实测:裸 `k3.1` 被 endpoint 拒绝并明示可用 ID;`k3.1-pro` 出字 200 带 thinking)。
继续跑 k3 = 主动放弃新一代模型;而全局默认切模型会把交互会话与编排器绑死在一起,
不可独立回滚。

## 方向

runner 显式化:L1 → `--model k3.1-pro`(对齐 T-2026-0908-003 L2/L3→k2.6 的既有显式
驾驶员模式),relay 侧**零改动**(未知 model 走 defaultChain,kimi1-4 `model:null`
透传,已实证)。ai-factory 仓库内闭环,不动 D:\Tool。

## 范围

1. `orchestrator/daemon/runner.py`:`_driver_for_level` L1 返回 `'k3.1-pro'`(原 None)
2. `orchestrator/adapters/claude_code.py`:`DRIVER_MODELS` 增加 `'k3.1-pro'`
3. `scripts/canary-report.py`:DRIVER_OF L1 标签 `'k3'`→`'k3.1-pro'`
4. `docs/orchestrator-guide.md`:路由表 L1 行更新
5. 测试先红后绿:`test_level.py`(driver 映射)+ `test_claude_code_adapter.py`(白名单)
6. 真实链路冒烟:`claude -p --model k3.1-pro` 经 relay 出字(非 mock)

## 不做

- relay(D:\Tool)任何改动——defaultChain 原生覆盖,改了反而把 k2.6/gpt 兜底语义绑死
- zen-k3 兜底模型(保持 kimi-k3;zen 侧 k3.1 可用性与费率未核,另议)
- k2.6 路由组、dsh(deepseek-v4-flash)、orchestrator.yaml models.dev/qa
- 水位闸口径:ledger resource 仍记 `k3`(kimi* 前缀计量不变,周水位连续)
- 交互式 CLI 全局默认模型(用户侧配置,不属本单)
- `k3.1-pro-highspeed` 变体(默认 pro;highspeed 留作后续观察项,boss 未点名为它)

## 风险与回滚

风险:k3.1-pro 行为回归影响全部后续 L1 工单执行质量;水位计费曲线可能变化。
回滚:单行还原 `_driver_for_level` L1 → None(恢复隐式默认),秒级。
观察:发布后一周看 relay /__stats 错误率与水位曲线(本单 L3 免观察窗,人工看)。
