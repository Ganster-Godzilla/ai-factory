# PRD-T-2026-0829-001: 阶段产物与门禁口径统一

> Phase 1 产物。门禁:templates/gate-checklists/phase1-gate.md
> 来源:工单流角色提示词为 M1 极简版(产物仅 prd.md/design.md/tasks.yaml),与技能流的全阶段产物规范脱节。
> 总原则:**每个阶段有可枚举的标准产物清单;门禁不只查"存在",还要查"必含要素";两流口径统一但定位不变。**

## Why(问题与价值)

当前工单流各阶段产物口径残缺,与技能流全阶段规范脱节,造成三类真实损失:

1. **产物断层**:工单流只有 P1 prd.md、P2 design.md/tasks.yaml 三类产物;P0 提案、P1 功能清单/歧义澄清、P3 验收留痕、P4 验收报告、P5 发布记录/观察窗报告均无标准口径,阶段推进缺乏可追溯证据链。
2. **门禁偏松**:G2 产物验收闸门(EXPECTED_ARTIFACTS)只校验"存在且非空",不校验产物必含要素——一份只有标题的空壳 PRD 也能过闸(参照 T-2026-0828-003 暴露的"PM 未写 PRD 仍推进"教训)。
3. **口径漂移**:角色提示词(pm.md/architect.md/qa 等)各自约定产出,缺统一清单做事实标准,新增角色/阶段时无据可依,工单流与技能流对"同一阶段该交什么"答案不一致。

不修的代价:阶段推进质量不可信(空壳产物过闸)、回溯断链(P4/P5 无记录无法复盘)、两流协作口径冲突(人机混合场景产物对不上)。

## What(范围与边界)

**范围内:**

| 编号 | 需求 | 概述 |
|---|---|---|
| R1 | 全阶段标准产物清单 | 定义并写死 P0–P5 各阶段标准产物:P0 提案文档(问题/方向/范围/不做);P1 `<id>-prd.md` + `<id>-功能清单.md` + `<id>-歧义澄清记录.md`;P2 `<id>-design.md` + `<id>-tasks.yaml`(已有);P3 任务级验收记录;P4 `<id>-验收报告.md`(已有事实标准,正式化);P5 发布记录(合并清单)+ 观察窗报告 |
| R2 | 角色提示词改写 | pm.md/architect.md/qa 等角色提示词按 R1 清单改写,产出物与命名逐一对应 |
| R3 | G2 闸门逐件校验 | EXPECTED_ARTIFACTS 按 R1 清单逐件校验存在且非空,缺件即阻断并指明缺哪件 |
| R4 | 门禁要素口径 | 每阶段门禁给出明确检查口径:不只查产物存在,还查产物必含要素(如 PRD 必含 Why/What/验收标准节;tasks.yaml 必过 slicer 契约校验) |
| R5 | 存量不追溯 | 新口径只对本单合入后新建工单生效,存量工单不回溯补产物 |

**范围外:**

- 不合并工单流与技能流:工单流=自动执行,技能流=人机交互,两流定位不变,本单只统一产物与门禁口径。
- 不改变 P0→P5 状态机骨架与人工审批节点。
- 不新增阶段,不调整既有产物格式之外的文件布局(如 PRD 存放路径约定不变)。
- 不做 dashboard/UI 呈现改造。

## 功能清单

| # | 功能 | 优先级 | 验收标准 |
|---|---|---|---|
| F1 | 全阶段产物清单定义(P0–P5) | P0 | 见 AC-1 |
| F2 | 角色提示词按清单改写 | P0 | 见 AC-2 |
| F3 | G2 闸门按清单逐件校验 | P0 | 见 AC-3 |
| F4 | 各阶段门禁要素口径定义 | P0 | 见 AC-4 |
| F5 | 存量工单不追溯声明与生效边界 | P1 | 见 AC-5 |

## 非功能需求

- **单一事实源**:全阶段产物清单集中定义于一处(配置或常量),角色提示词、G2 闸门、门禁检查清单均引用同一来源,禁止各自维护副本导致口径漂移。
- **可执行口径**:每条门禁要素必须可被自动检查或人工逐项打勾,禁止"内容合理""质量达标"类不可判定措辞。
- **兼容**:存量工单状态与已落盘产物不受影响;新口径生效点(按工单创建时间或合入版本)需明确可判。

## 验收标准

- **AC-1(产物清单)**:存在一份权威清单覆盖 P0–P5,每阶段列明产物文件名(含 `<id>` 占位命名规则)、必含要素、产出角色;清单与技能流对应阶段口径逐项对齐,差异为零或逐条有显式说明。
- **AC-2(提示词改写)**:逐一检查 pm/architect/qa 等角色提示词,其"产出物"段落与 AC-1 清单一致;构造 P1 阶段 PM 调用,产物同时包含 `<id>-prd.md`、`<id>-功能清单.md`、`<id>-歧义澄清记录.md` 三件,缺任一件视为不达标。
- **AC-3(G2 逐件校验)**:构造某阶段缺任一件预期产物的用例,闸门阻断且报错指明缺失产物名;产物全部存在但任一件为空文件,同样阻断;全部存在且非空时放行。
- **AC-4(要素口径)**:每阶段门禁检查清单条目化,至少覆盖:P1 PRD 必含 Why/What/验收标准三要素,P2 tasks.yaml 必过 `slicer.load_task_list` 契约校验(查重/依赖存在/循环依赖),P3 每任务有 acceptance 结果留痕,P4 验收报告正式化为标准产物;构造"产物存在但缺必含要素"的用例,对应门禁判失败并指出缺失要素。
- **AC-5(存量不追溯)**:新口径合入前已存在的工单,在其后续阶段推进中不因缺新清单产物被阻断;合入后新建工单全程按新口径执行;生效边界判定规则在文档中明确。

## 歧义与开放问题

→ 逐条登记到 歧义澄清记录.md

1. P0 提案文档的文件名与存放路径未定(如 `<id>-提案.md` 放 `document/business/` 还是 `pool/` 侧),需 P2 设计时明确。
2. P5 观察窗报告的观察时长与报告要素(看什么指标、多少天)需定义口径。
3. "要素校验"的自动化边界:哪些要素可机器判定(如 tasks.yaml 契约)、哪些只能人工勾核(如 PRD 的 Why 是否成立),需分级说明。
4. 角色提示词改写的覆盖范围:除 pm/architect/qa 外,p0 提案角色、release 角色是否一并在本单改写,需确认。
