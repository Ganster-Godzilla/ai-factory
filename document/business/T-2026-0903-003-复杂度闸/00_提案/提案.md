# 提案:复杂度闸接入常设质量闸

- 工单:`pool/tickets/T-2026-0903-003.yaml`
- 类型:feature / 平台质量(常设闸)
- 溯源:2026-09-03 ruff/radon 扫描(用户决定二档);关联 R 系规则

## 问题

ai-factory 无圈复杂度闸。ruff/radon 一扫即发现 `run_dev_tasks` 46(F 级)、
`main` 25、`check_gate` 24 等上帝函数——**函数在一次次改动中越变越胖,无人拦截**。
没有常设闸,复杂度只会继续恶化,下次还得靠人工大扫除。

## 方向

把圈复杂度检查接入常设质量闸,**只拦增量、豁免存量基线**,防函数继续变胖:

- 工具:`radon cc`(已在 tmp venv 验证可跑),阈值 C 级(cc > 15 即拦新函数)。
- 接入点:与 `scripts/check-pool-load.py` 同级的独立脚本
  `scripts/check-complexity.py`,合 main 前随守卫一起跑。
- **基线豁免**:现状超标函数(run_dev_tasks 46 / main 25 / check_gate 24 /
  DshAdapter.run 23 / load_deploy_config 21 等)冻结进基线清单,
  只拦"基线外新增超标函数"或"基线函数复杂度继续升高";基线函数被改低即放行。
- 闸语义:超标即非零退出 + 打印超标函数清单(与 gitguard 同风格)。

## 范围

新增 `scripts/check-complexity.py` + 基线清单文件 + 接入合 main 守卫流程
(文档说明);不改 ruff/radon 本身,不动既有 lint 闸(stack-profile pyflakes)。
验收标准:

1. `check-complexity.py` 对当前仓返回 0(基线豁免生效,不拦存量)。
2. 人为新增一个 cc>15 的函数 → 脚本返回非零并点名。
3. 基线函数复杂度升高(如 run_dev_tasks 46→50)→ 非零;降低(46→15)→ 放行。
4. 与 check-pool-load 同跑,互不干扰。

## 不做

- 不强制拆分存量超标函数(那是 002 的事;本闸只防新增/恶化)。
- 不接 ruff 全规则集(风格噪声大);只闸圈复杂度。
- 不改 CI(暂无远端 CI;闸走本地合 main 守卫)。
