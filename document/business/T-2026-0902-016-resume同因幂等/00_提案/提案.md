# 提案:resume 同因幂等提示(防确定性 bug 连撞)

- 工单:`pool/tickets/T-2026-0902-016.yaml`
- 类型:feature / 平台改进(编排器 statemachine / CLI / dashboard)
- 优先级:normal
- 关联规则:R12(`.claude/rules-registry.md`)
- 溯源事故:T-2026-0902-011(deploy 路径闸确定性误报被反复 resume 三连挂,
  incident T-2026-0902-014 复用三次)

## 问题

工单挂起后,`resume` 只负责把状态拨回 `resume_state` 重跑,**不校验"本次与上次
挂起是否同一根因"**。确定性平台 bug(不随重试消失)会被反复 resume 连撞:

- T-2026-0902-011 的 deploy 依赖闸读错路径(`releases/current` 服务器上不存在),
  是**确定性误报**——重试多少次都一样。但它被 resume 重跑三次,三次撞同一闸、
  三次挂起,还连锁触发 incident 复用三次。
- resume 的"无脑重跑"放大了单点平台 bug 的破坏面。

## 方向

resume(CLI `orc resume` + dashboard `/resume` POST)时,若工单的 `reason_code`
与该单**上一次挂起的 reason_code 相同**,则默认**警告**:"上次因同一原因
(`<reason_code>`)挂起,根因未变,直接 resume 大概率再撞同一闸,请先修根因。"
需显式确认(CLI `--force` / dashboard 确认勾选)才执行;根因已修(reason_code
变化)则正常放行。比对依据:事件流最近一次 `suspended` 事件的 `reason_code`。
提示/确认写事件流留痕。

## 范围

`orchestrator/daemon/statemachine.py`(resume 入口同因检测)+ `cli.py`(`--force`)+
`dashboard/app.py`(确认勾选)+ 对应测试。验收标准:

1. 同一 reason_code 连续 resume:第二次起必须给警告,未带 `--force`/确认时不执行。
2. 带 `--force`(或 dashboard 确认)→ 正常 resume,留"同因强制恢复"事件。
3. 根因已修(reason_code 与上次不同)→ 无警告直接放行。
4. 工单无历史挂起事件(首次 resume)→ 正常放行。
5. 现有 resume 正常路径零回归,`pytest tests/` 全绿。

## 不做

- 不做"自动诊断根因是否已修"(仅靠 reason_code 是否变化作代理,不读代码)。
- 不改 suspend 的触发逻辑,只在 resume 入口加幂等提示。
